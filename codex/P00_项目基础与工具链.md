# P00｜项目基础、工具链与可构建空插件 — Codex 可执行任务

> **开始条件：** 新仓库，已放入全部 Markdown 资料；如果已有源码，先检查差异和兼容性。。这是完整的执行任务，不是仅供讨论的需求草案。

## 本阶段唯一目标

让工程可重复构建：独立 DSP 核心库、最小音频插件、离线渲染程序、测试体系与许可记录。**此阶段不实现钢琴声音。**

## 必须实现的事项

1. 检查机器 OS/CPU/编译器/CMake/Python/Codex/JUCE 环境，输出 `experiments/P00/environment.md`。不得猜测缺失版本。
2. 创建 C++20 CMake 工程；将 JUCE 9.x 固定到经实际验证的 tag/commit（若暂不可下载，先建立可独立编译 `PianoDSP` 的工程和明确的 submodule 待办）。
3. 建立 `src/dsp`、`src/model`、`src/performance`、`src/plugin`、`tools/offline_render`、`tools/analyzer`、`tests`、`experiments`，对应 `docs/01`。
4. 创建 `PianoDSP` 库，最小 `PianoEngine::prepare/process/reset`，零值输出；JUCE `AudioProcessor`（IS_SYNTH, MIDI）调用其接口，按平台创建 VST3/Standalone，macOS 构建 AU。
5. 创建 `offline_render` CLI，支持生成 48 kHz/32-bit float、2ch WAV 与可设置时长；当前输出零声。验证 WAV header 与文件长度。
6. 建立 CTest：工程加载、音频缓冲边界、无输出噪声、重复 prepare/reset 和 sample offset 参数检查。
7. 写 `README-build.md`（Debug/Release、Windows/macOS 命令）和 `THIRD_PARTY_LICENSES.md`，保存所用 JUCE commit 与许可证策略的待确认项。
8. 加入基础 CI 示例（不会假设已能跑商业编译 runner）。

## 实际测试与复现

- 实际运行 `cmake -S . -B build/...`、`cmake --build ...`、`ctest --test-dir ... --output-on-failure`；Windows 或 Xcode 多配置时加 `--config`。
- 验证可执行离线渲染器能产出正确 WAV，并报告其 SHA-256 与测得样本数。
- 如果 JUCE 可构建，使用最低限度宿主加载/插件扫描；没有可运行宿主时标 `NOT RUN`。
- Debug/Release 均需报告真实结果；若环境缺依赖，在报告中说明可以运行的子集。

## 统一执行协议（每阶段必做）

1. 在开始改动前读取根目录 `AGENTS.md`、`README.md`、`docs/06_阶段路线图与验收门.md`、本阶段指定的文档与前阶段实际 `PHASE_REPORT`。
2. 检查 `git status`；不要覆盖未知或未提交的用户更改。提出短计划后实际编辑代码/文档。
3. 明确真实运行过的命令与结果（PASS / FAIL / SKIP / NOT RUN）。失败不得消失；禁止伪造音频、图表、编译日志或 CPU 数据。
4. 将输出写入 `experiments/P00/`，至少包含 `PHASE_REPORT.md`，实际测试日志及物理声学结果；无音频结果时解释原因。
5. 保持插件 `processBlock` 与 DSP `process` 无动态分配、锁等待、文件/网络 IO 和同步日志；保留最小回滚路径。
6. 完成后给出更改文件、复现命令、测试状态、定量结果、已知近似、风险及阶段门结论；如不满足，则标为 `BLOCKED` 并停止，而非直接执行下一阶段。
